### 1.3 内存初始化划分

数据库启动时，`max_process_memory` 被划分为**共享内存**与**动态内存**两部分。这一划分在实例启动时完成，是所有内存调度行为的起点。

```
┌──────────────────────────────────────────────────────────────┐
│              max_process_memory = ①______ MB                 │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  共享内存段 ②______ MB（启动时一次性分配，运行期固定）           │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  shared_buffers          ③______ MB                    │  │
│  │  ┌──────────────────────────────────────┐              │  │
│  │  │  可让渡部分 (③−④)______ MB            │ ← 允许调出   │  │
│  │  ├──────────────────────────────────────┤              │  │
│  │  │  保留下限   ④______ MB                │ ← 不得调出   │  │
│  │  └──────────────────────────────────────┘              │  │
│  │                                                        │  │
│  │  cstore_buffers          ⑤______ MB                    │  │
│  │  data cache              ______ MB                     │  │
│  │  wal_buffers             ______ MB                     │  │
│  │  其他共享结构            ______ MB                      │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  动态内存 ⑥______ MB                                          │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  会话上下文、算子 work_mem 从这里支取                     │  │
│  │  空载已用约 ______ MB                                   │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**填写与取数说明：**

| 编号 | 量 | 取数方式 |
|---|---|---|
| ① | `max_process_memory` | 取自 1.2 配置值 |
| ② | 共享内存段总量 | 实例启动日志 / 系统视图实测，**不等于 ③** |
| ③ | `shared_buffers` | 取自 1.2 配置值 |
| ④ | 共享池保留下限 | 由参评方声明：其方案承诺**在任何压力下都不会调出**的那部分共享缓存。未声明下限的方案按 ④ = 0 记录，并在结论中注明 |
| ⑤ | `cstore_buffers` | 取自 1.2 配置值 |
| ⑥ | 动态内存 | 见下方派生公式，并以实例启动日志实测值为准 |

**两点必须写清：**

1. **共享内存段 ② ≠ `shared_buffers` ③**。后者只是前者的一部分，其余为列存缓冲、数据缓存、缓冲区描述符、锁表等结构。凡涉及内存容量的计算，一律使用 ②，不得用 ③ 代替，否则动态内存会被系统性高估。

2. **动态内存 ⑥ 是派生量，不是可配置参数**。它由原生 openGauss 在启动时算出：

   ```
   动态内存 ⑥ = max_process_memory ① − 共享内存段 ② − cstore_buffers ⑤ − 后台预留
   ```

   实例启动日志中会输出后台预留与动态内存的实际值，形如：

   ```
   Set max backend reserve memory is: ______ MB, max dynamic memory is: ______ MB
   ```

   **验收时以日志实测值为准，不接受按公式估算的申报值。**

### 1.4 由此得到的容量基准

本节的三个数值是全部测试场景的分档依据，由 1.2、1.3 直接推导，**与参评方案的实现方式无关**，因此对所有方案通用。

设单个 AP 排序会话的目标内存为 **W MB**（取值见第二部分场景定义）。

| 内存来源 | 容量 | 说明 | 折合 W MB 会话数 |
|---|---|---|---|
| 动态内存 | ⑥______ MB | 原生路径，不依赖任何调度机制 | ⑥ ÷ W ≈ ______ |
| 共享池可让渡部分 | (③−④)______ MB | 须由参评方案主动调度才能获得 | (③−④) ÷ W ≈ ______ |
| **合计** | ______ MB | | **≈ ______** |

```
会话数：  1  …  N₁  │  N₁+1  …  N₂  │  N₂+1 ...
         └──────────┘ └─────────────┘ └────────
          动态内存       可让渡部分       无内存可给
         （原生即可满足） （必须调度）     （只能排队 / 降级）
                        ↑              ↑
                   调度应当开始      共享池应当停在保留下限
```

**三个关键分界点（填定后作为场景分档）：**

| 分界点 | 定义 | 本次取值 |
|---|---|---|
| **N₁** | 动态内存耗尽，再增加会话必须动用共享池 | ______ 个会话 |
| **N₂** | 可让渡部分也耗尽，共享池抵达保留下限 | ______ 个会话 |
| **> N₂** | 无内存可供分配 | —— |

> **会话数的校准要求：** AP 会话的**实际**内存占用通常低于名义申请值（受行宽、对齐、算子实现影响）。分档不得按名义值换算，须在**原生 openGauss（关闭参评方案）**下实测单会话真实占用，再按目标总内存反算会话数；该会话数由「启用组」与「关闭组」**共用**，以保证对照公平。实测方法见第三部分测试脚本。

## 二、测试场景

### 2.1 为什么这样测

**难题的实质。** openGauss 在实例启动时就把 `max_process_memory` 一次性劈成共享内存与动态内存两块，此后运行期这条边界固定不动。由此产生典型的「一边闲死、一边饿死」：TP 空闲时 `shared_buffers` 里大量缓存页无人问津，同一时刻并发的 AP 排序却因动态内存不足而落盘；TP 高峰时又反过来需要缓存。参评方案要解决的，就是让这条边界在运行期能够移动。

**因此验收不考核「方案跑得快不快」，只考核四件事：**

| # | 问题 | 通俗说法 |
|---|---|---|
| 1 | 该让的时候，让不让得动 | 动态侧不够用时，能否真的把共享内存转过去 |
| 2 | 让到什么程度会停 | 有没有下限保护，TP 的缓存不会被抽干 |
| 3 | 让无可让时怎么办 | 过载是否有序，而不是失控或静默降级 |
| 4 | 要得回来吗 | TP 需要时，让出去的内存能不能收回 |

这四件事无法在单一负载下观察。必须构造一条**单调升压的阶梯**，让系统依次穿过 §1.4 的两个分界点 N₁、N₂，**每一档只暴露一种行为**——只有这样，才能把「压根没发生」和「发生了但无效」区分开。这就是五个 step 的由来：

| step | 压力位置 | 检验的问题 | 对应能力 |
|---|---|---|---|
| ① | 远低于 N₁ | 不该动的时候，会不会乱动 | 静止性（基线） |
| ② | 越过 N₁ | 该让的时候，让不让 | 让渡触发 |
| ③ | 到达 N₂ | 一直让下去，会不会停 | 下限保护 |
| ④ | 超过 N₂ | 让无可让，怎么办 | 过载兜底 |
| ⑤ | ④ 之上反向加 TP | 要不要得回来 | 双向可逆 |

**① 同样是必测项。** 内存宽裕时发生不必要的调度动作（反复借还、无谓反压），本身就是缺陷，而且会掩盖后续档位的观察。

**三条判定原则：**

1. **每一档都以「关闭方案的原生 openGauss」为对照。** 原生 openGauss 在内存不足时本来就有落盘这一既有兜底，**查询能跑完不等于方案有效**；只有相对原生产生了可观测的差异，才算方案起了作用。两组必须在同一实例、同一份数据、同一组负载参数下连续执行，唯一变量是方案的开关。
2. **判据只落在外部可观测量上**：`shared_buffers` 实际值、排序是否落盘及落盘量、`buffer_hit`、TPS、排队/拒绝计数、查询耗时。**不采信方案自报的内部状态**——自报"已授信 N MB"不等于算子真的用到了 N MB，须以 `EXPLAIN (ANALYZE)` 的 `Sort Method` 为准。
3. **压力只增不减，各档时长一致**（例：每档 2 分钟），档间不重启实例、不重建数据。

> **以下五档中的数字（512 MB、4 个、7 个、2048 MB 等）均为举例**，来自一次已完成的实测环境。实际验收时，全部数值由 §1.2–§1.4 填定后重新推导：`W` 为单 AP 会话目标内存，`N₁`/`N₂` 为两个分界点，`③`/`④` 为共享池初值与保留下限。

---

### step ① 内存宽裕

| 项 | 值（举例） |
|---|---|
| TP | 2 worker |
| AP | 2 会话 × 128 MB |
| AP 内存需求 | 256 MB |
| 位置 | 远低于动态内存 2134 MB（即 ≪ N₁） |

**验收目标：** 内存充裕，AP 直接从动态内存获得所需内存，**共享池不发生任何让渡**，TP 吞吐不受影响。

本档为基线参照，同时检验方案的静止性——**不该动的时候不动**。

---

### step ② 越过 N₁ —— 开始让渡

| 项 | 值（举例） |
|---|---|
| TP | 2 worker |
| AP | **超过 4 个** 512 MB 等效会话（即 > N₁） |
| AP 内存需求 | > 2134 MB |
| 位置 | 越过动态内存上限 |

**验收目标：方案开始把共享内存转给动态侧。** 表现为：

- `shared_buffers` 从初值开始下降
- AP 仍能拿到接近 W 的排序内存，**不落盘**（`Sort Method: quicksort`）
- TP 吞吐在缓冲池缩小后仍保持可接受水平

**这是验收核心价值的关键档位**——若此处不动，后续各档均无从谈起。

---

### step ③ 到达 N₂ —— 让渡停止，下限保护生效

| 项 | 值（举例） |
|---|---|
| TP | 2 worker |
| AP | **7 个** 512 MB 等效会话（即 = N₂） |
| AP 内存需求 | ≈ 3670 MB |
| 位置 | 动态内存 + 全部可让渡部分耗尽 |

**验收目标：让渡停止，`shared_buffers` 停在保留下限 ④ 不再下降。** 表现为：

- `shared_buffers` 降至 ④ 后**不再继续下降**
- 让渡动作停止
- TP 仍能依靠这部分保底缓存维持运行，`buffer_hit` 不崩塌

**下限保护是 TP 的最后一道防线**——没有它，AP 可以把缓冲池抽干，TP 将因缓存崩塌而不可用。

---

### step ④ 超过 N₂ —— 过载兜底

| 项 | 值（举例） |
|---|---|
| TP | 2 worker |
| AP | **超过 7 个** 512 MB 等效会话（即 > N₂） |
| AP 内存需求 | > 3670 MB |
| 位置 | 让无可让 |

**验收目标：新到的 AP 被有序处置，而不是继续挤占内存。** 可接受的处置方式由参评方声明（排队等待、拒绝、降级落盘等），但必须满足：

- 处置是**明示且可观测**的（有计数、有日志，能统计到）
- 整体内存不被突破，实例不因此不可用
- 不出现查询失败，或失败被明确定义并可预期

**这一档检验内存耗尽后的兜底行为**：是有序处置，还是静默降级、甚至失控。注意原生 openGauss 在此档通常也能靠落盘全部跑完且零报错——因此**"没报错"不构成达成**，须与原生对照才有意义。

---

### step ⑤ TP 流量增加 —— 反向回收，保住 buffer_hit

| 项 | 值（举例） |
|---|---|
| TP | **2 worker → 8 worker** |
| AP | 保持 step ④ 的会话数不变 |
| 变化方向 | 由 AP 侧加压转为 TP 侧加压 |

**验收目标：`shared_buffers` 回升，`buffer_hit` 得到保护，同时每个 AP 会话可用内存相应下降。** 表现为：

- 先前让渡出去的内存被**收回共享池**，`shared_buffers` 上涨
- `buffer_hit` 止跌回升，最低点显著优于对照组
- 代价是 AP 变慢或落盘——**这是预期内的代价，不算缺陷**

**这一档检验调度的双向性**：前四档看"能不能把内存让出去"，这一档看"TP 需要时能不能要回来"。**单向让渡不是调度，双向可逆才是。**

### 五档汇总

| step | AP 会话数（W 等效） | 所处区间 | 验收目标 |
|---|---|---|---|
| ① | 远小于 N₁（例：2 个 × 128 MB） | 内存宽裕 | 不让渡，TP 不受影响，无多余动作 |
| ② | **> N₁**（例：> 4 个） | 越过动态内存 | **开始让渡**，`shared_buffers` 下降，AP 不落盘 |
| ③ | **= N₂**（例：7 个） | 可让渡部分耗尽 | **让渡停止**，停在保留下限 ④ |
| ④ | **> N₂**（例：> 7 个） | 让无可让 | **有序兜底**，整体内存不被突破 |
| ⑤ | 同 ④，TP 2→8 worker | TP 侧加压 | **共享池回升**，`buffer_hit` 保住 |

## 三、测试脚本

### 3.1 工具与版本

两类负载统一使用 **gsbench**，验收双方使用同一版本，版本号记入测试记录。

| 项 | 内容 |
|---|---|
| 仓库 | **https://github.com/sqlrush/gsbench** |
| 版本 | v1.1.8（以验收启动时的最新发布为准） |
| 安装手册 | `docs/gsbench/INSTALL.md` |
| 配置手册 | `docs/gsbench/CONFIG.md` |
| 本次实际版本 | ______（填定后不再变更） |

选用 gsbench 的理由：101–103、201–202 属于**固定 worker 模型**——按声明的 worker 数建立独立会话，全部就绪后统一开始加压，压力可精确预算、可复现，适合按会话数分档。同时 201 会只读检查排序内存与落盘情况并输出证据，正是本方案需要的判据来源。

### 3.2 准备

```bash
chmod 600 configs/gsbench.cfg
export GSBENCH_CONFIG="$PWD/configs/gsbench.cfg"
export GSBENCH_PASSWORD='数据库密码'

gsbench scenarios              # 查看场景清单与风险等级
gsbench doctor                 # 环境体检
gsbench init --size <规模> --dry-run
gsbench init --size <规模>     # 造数，规模须满足 §1.5 的硬性要求
```

**造数只做一次，两组共用。** 档间与组间均不得重建数据——重建会改变物理分布与缓存状态，破坏对照。

### 3.3 TP 负载：场景 101（`tp_cpu`）

模拟 OLTP 点查，既提供 TPS 基线，也充当「被保护对象」。启动时对目标表做键采样，保证点查随机命中全表而非热点区，`buffer_hit` 才会随缓冲池增减真实波动。

```bash
gsbench run 101 --workers 2 --duration 8m     # step ①~④
gsbench run 101 --workers 8 --duration 2m     # step ⑤
```

### 3.4 AP 负载：场景 201（`memory_workmem_sort`）

按声明的 worker 数拉起等量的排序会话，每个 worker 使用独立的 `work_mem`——这正是 §1.4 中「W MB × N 个会话」的压力模型。

```bash
gsbench run 201 --workers <N> --work-mem <W> --duration 2m
```

201 在运行前会只读检查工作集、Sort 内存与落盘情况；不满足预期时**只告警、不自动调小数据或参数**，因此实测到的落盘就是真实结论，不会被工具悄悄掩盖。它还会在标定事务中 `SET LOCAL explain_perf_mode=normal`（事务回滚后自动恢复，不影响其他会话），以保证能读到 `Sort Method` 与 `Memory Usage`——`pretty` 模式下的 `Peak Memory` 不作为落盘证据。

### 3.5 五个 step 如何用 gsbench 组合出来

五个 step 都需要 **TP 与 AP 同时施压**。101 与 201 均为固定 worker 模型，可在同一次运行中一起拉起：

```bash
gsbench run -s 101,201 -d 2m
```

**但有一条工具约束必须遵守：201/202 的命令行覆盖一次只允许选择一个场景。** 也就是说 `-s 101,201` 与 `--workers/--work-mem` 不能混用，否则无法分别指定 TP 与 AP 的 worker 数。正确做法是把两个场景的参数写进 `configs/gsbench.cfg`，再用 `-s 101,201` 一次拉起：

```ini
[scenario.tp_cpu]
workers = 2                    ; 101 的 TP worker 数

[scenario.memory_workmem_sort]
workers = 5                    ; 201 的排序 worker 数，逐档调整
work_mem = 512MB               ; 单会话目标内存 W
```

据此，五档的编排如下（`N₂'` 表示超过 N₂ 的取值）：

| step | `tp_cpu.workers` | `memory_workmem_sort.workers` | 命令 |
|---|---|---|---|
| ① | 2 | 远小于 N₁，且 `work_mem` 取小档（例 128MB） | `gsbench run -s 101,201 -d 2m` |
| ② | 2 | **N₁ + 1** | `gsbench run -s 101,201 -d 2m` |
| ③ | 2 | **N₂** | `gsbench run -s 101,201 -d 2m` |
| ④ | 2 | **N₂'**（> N₂） | `gsbench run -s 101,201 -d 2m` |
| ⑤ | **8** | 同 ④ 的 N₂' | `gsbench run -s 101,201 -d 2m` |

每档执行前改写配置中的两个 worker 值，其余一律不动。**档间不重启实例**；每档结束后等待固定的静默窗口（例 60 秒）再进入下一档，避免上一档的残留影响观测。

> 若参评方案的处置方式使 201 的固定 worker 无法稳定占住内存（例如会话被提前释放），可改用**持有型游标会话**作为补充：`BEGIN` → `SET LOCAL work_mem` → `DECLARE CURSOR ... ORDER BY` → `FETCH 1` 后不再取、不提交。排序是阻塞算子，`FETCH 1` 会强制排完全部数据并建立完整排序状态，游标保持打开即可持续占用内存。此路径与 201 二选一，全程只用同一种，不得混用。

### 3.6 会话数校准（强制步骤）

**AP 会话的实际内存占用通常低于名义申请值**（受行宽、对齐、算子实现影响，实测可低 7%~10%）。若按名义值直接换算会话数，实际压力会系统性偏低，导致 N₁、N₂ 两个分界点根本没被跨过——此时观察到的"没让渡"是压力不足造成的，而非方案缺陷。

因此每次实验开始时必须先实测，再按实测值反算会话数：

```
实际会话数 = ⌈目标总内存 ÷ 单会话实测占用⌉
```

实测方法：在原生模式下用与压测**完全相同**的排序语句跑 `EXPLAIN (ANALYZE)`，读取 `Sort Method` 行：

```
Sort Method: quicksort  Memory: ______kB      ← 全内存完成，取此值
Sort Method: external merge  Disk: ______kB   ← 已落盘，测量无效
```

**两条硬性要求：**

1. **测量必须在原生模式（关闭参评方案）下进行。** 方案开启时若排序落盘，`EXPLAIN` 输出的是 `Disk` 而非 `Memory`，测不到真实驻留内存。
2. **测量只做一次，两组共用同一组会话数。** 若两组各自测量，会得到不同的并发数，就不再是对照实验。

校准结果记入下表，并随测试记录一并提交：

| 场景目标 | 目标总内存 | 名义会话数 | **实际启动会话数** |
|---|---|---|---|
| 越过 N₁（step ②） | ______ MB | ______ | ______ |
| 到达 N₂（step ③） | ______ MB | ______ | ______ |
| 超过 N₂（step ④⑤） | ______ MB | ______ | ______ |

测量值不写死在脚本里，每次实验重新测，以适应数据分布或环境变化。

### 3.7 A/B 编排与采样

**编排：** 同一实例连续跑两组，先「启用参评方案」，静默 30 秒后切「关闭（原生 openGauss）」，两组使用完全相同的五档编排、负载参数与会话数。切换后必须回读确认开关已实际生效，未生效即中止实验。

**采样：** 每秒记录一次数据库状态与统计，至少覆盖：

| 采样项 | 用途 |
|---|---|
| `shared_buffers` 实际值 | 让渡深度、是否触及下限 ④ |
| 动态内存已用量 | 需求是否真的进入了内存记账 |
| `buffer_hit` | step ⑤ 的核心判据 |
| 事务数 / TPS | 各档 TP 吞吐 |
| 方案自报的排队 / 拒绝 / 降级计数 | 仅作参考，不作为达成判据 |
| 会话与服务器日志 | 错误、降级、超时的证据 |

采样连接自身不得成为压力源；若两组采样密度差异明显，须在结果中说明，并确保达成判定只建立在不受采样密度影响的量上（极值、累计计数增量、`EXPLAIN` 直接测量、gsbench 总量统计）。
