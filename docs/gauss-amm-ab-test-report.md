### 1.2 原生 openGauss 的内存约束（两组共同前提）

本节只涉及 openGauss 自身的参数。**这些约束在 AMM 开启与关闭两组中完全相同**，是对比的公共基线。

| 参数 | 值 | 级别 | 含义 |
|---|---|---|---|
| `max_process_memory` | **7424 MB** | postmaster | 数据库进程内存总上限（本次由 4 GB 调整而来，理由见 §1.2.2） |
| `enable_memory_limit` | **on** | postmaster | 内存保护，实际生效 |
| `max_dynamic_memory` | **2134 MB** | 派生 | 动态内存上限，`work_mem` 从此支取 |
| `shared_buffers` | 2048 MB | postmaster | 共享缓冲池 |
| `cstore_buffers` | 512 MB | postmaster | 列存缓冲（本测试无列存表） |
| `wal_buffers` | 16 MB | postmaster | WAL 缓冲 |
| `max_connections` | 200 | postmaster | 最大连接数 |
| `work_mem` | 会话级设定 | user | **单个算子**的内存预算 |

`max_process_memory` 限定进程可用内存总量，共享内存与动态内存都在其中：

```
max_process_memory = 7424 MB  ← 进程总上限
│
├─ 共享内存段 = 4429 MB（实测，见 §1.2.1）
│   ├─ shared_buffers   2048 MB   ← 仅占共享内存的 46%
│   ├─ cstore_buffers    512 MB
│   ├─ data cache        384 MB
│   ├─ wal_buffers        16 MB
│   └─ 其他共享结构    ~1469 MB
│
└─ 动态内存 = 2134 MB（实测）
    └─ 会话上下文、算子 work_mem 等从此支取
```

**这两个数是本次全部压力档位的推算依据**：AP 的 `work_mem` 从 2134 MB 的动态内存中支取，用满之后才谈得上向 2048 MB 的共享池借。

#### 1.2.1 共享内存 ≠ `shared_buffers`

这是一个容易误解、且直接影响压力档位设计的事实。

**实测共享内存段为 4429 MB，`shared_buffers` 只占其中 2048 MB（46%）。**

```
$ ipcs -m -i 0
bytes=4644538696        （= 4429 MB）
lpid=1057  cpid=1057    （gaussdb postmaster）
att_time=Tue Aug 11 17:13:40 2026
```

这个数字**不是推算，openGauss 自己也报同一个值**（见 §1.2.2 的启动告警：`shared memory (4429 Mbytes)`）。

可指认的构成：

| 项 | 大小 | 依据 |
|---|---|---|
| `shared_buffers` | 2048 MB | GUC |
| `cstore_buffers` | 512 MB | GUC（本测试无列存表，属闲置） |
| data cache | 384 MB | 启动日志 `set data cache size(402653184)` |
| `wal_buffers` | 16 MB | GUC |
| 小计 | 2960 MB | |
| 缓冲区描述符与映射哈希、锁表、事务槽、双写缓冲、段页式结构、AMM 自身共享状态 | 约 1469 MB | 随 `shared_buffers` 规模与 `max_connections=200`、`max_locks_per_transaction=256` 派生 |
| **合计** | **4429 MB** | |

> 最后一行无法逐项拆分：该 build 不提供 `pg_shmem_allocations`，也没有 `gs_shared_memory_detail()`，两个内省视图均不存在。故只能定性列出。

**结论：计算动态内存时必须用 4429 MB，不能用 2048 MB。** 二者相差 2381 MB，用错会使所有压力档位推算失真。

#### 1.2.2 内存保护的启用条件与本次配置调整

按原生 openGauss 的口径：

```
动态内存可用量 = max_process_memory − 共享内存 − cstore_buffers − UDF 预留
```

初始配置 `max_process_memory = 4GB` 时代入为负，内存保护无法初始化：

```
WARNING: Failed to initialize the memory protect for
         g_instance.attr.attr_storage.cstore_buffers (512 Mbytes)
         or shared memory (4429 Mbytes) is larger.
```

源码中共有**两道门闩**（`src/common/backend/utils/mmgr/memprot.cpp`）：

```c
// 门闩 1（:991-994）
int avail_mem = max_process_memory - cstore_buffers
              - (udf_memory_limit - UDF_DEFAULT_MEMORY) - (size >> BITS_IN_KB);
if (avail_mem < MIN_PROCESS_LIMIT) { ...初始化失败... }        // MIN_PROCESS_LIMIT = 2 GB

// 门闩 2（:1018-1021）
if (maxChunksPerProcess < (MIN_PROCESS_LIMIT >> BITS_IN_KB)) { // 2048 MB
    maxChunksPerProcess = 0;
    t_thrd.utils_cxt.gs_mp_inited = false;                     // 保护被关闭
}
```

逐档实测（每次均需重启）：

| `max_process_memory` | 门闩 1 | `max dynamic memory` | 门闩 2 | 保护状态 |
|---|---|---|---|---|
| 4 GB（初始） | ✗ 失败 | — | — | off |
| 6 GB | ✗ 失败 | — | — | off |
| 7 GB | ✓ 通过 | 1878 MB | ✗ < 2048 | **off** |
| **7424 MB（本次采用）** | ✓ 通过 | **2134 MB** | ✓ ≥ 2048 | **on** |

**由此得到一条重要约束：只要内存保护开启，动态内存就不可能低于 2048 MB。** 这是 openGauss 自身 `MIN_PROCESS_LIMIT` 的设计下限，测试无法把动态侧压得更紧。

**本次测试采用的配置**（较初始配置有一处调整，已重启生效）：

| 参数 | 初始 | 本次 | 说明 |
|---|---|---|---|
| `max_process_memory` | 4 GB | **7424 MB** | 使内存保护能够初始化 |
| `shared_buffers` | 2048 MB | 2048 MB | 被测对象，不变 |
| `cstore_buffers` | 512 MB | 512 MB | 不变（减少变量） |
| `enable_memory_limit` | off（初始化失败） | **on** | 结果，非直接设置 |

调整后的实测内存分解：

```
Set max backend reserve memory is: 348 MB, max dynamic memory is: 2134 MB

gs_total_memory_detail：
  max_process_memory    7424 MB
  max_dynamic_memory    2134 MB
  dynamic_used_memory    542 MB   （空载）
```

**这是本次压力档位设计的直接依据**：AP 可用的动态空间约 `2134 − 542 ≈ 1592 MB`，超出部分才需要向共享池借。

### 1.3 AMM 引入的内存模型与参数（仅开启组生效）

以下概念与参数**全部由 AMM 特性引入**，原生 openGauss 中不存在。在关闭组（`native_auto_mode=off`）中，AMM 不介入执行器内存分配，这些机制不参与 AP 的内存获取。

#### 1.3.1 AMM 把内存重新划分为两个池

AMM 在上述固定信封内部，引入了"共享池 ↔ 动态池"的可迁移结构：

| 概念 | 说明 |
|---|---|
| **共享池** | 即 `shared_buffers`，AMM 内部称 `active_mb`，上限 `max_mb` = 2048 MB |
| **动态池** | AMM 新增的概念，供 AP 算子使用 |
| **granule** | 迁移的最小单位，`gs_amm_granule_size_mb` = 64 MB；2048 MB 折合 **32 个** |
| **借（BORROW）** | granule 从共享池迁往动态池：共享减 64、动态加 64 |
| **还（TP_RECOVERY）** | 反向迁移 |

**借还是零和的**：两池之和不变，总量始终受 `max_process_memory` 约束。

#### 1.3.2 可迁移带宽

| 参数 | 值 | 说明 |
|---|---|---|
| `gs_amm_shared_buffers_min_mb` | 512 MB | **地板**，共享池不得低于此值（8 granule） |
| **可迁移带宽** | **1536 MB = 24 granule** | 2048 − 512 |

```
  2048 MB ┌─────────────────────────────────┐  ← max_mb，共享池上限
          │                                 │
          │   可迁移带宽 1536 MB（24 个 granule）│  ← 借出只能在这个区间内发生
          │                                 │
   512 MB ├─────────────────────────────────┤  ← 地板 shared_buffers_min_mb
          │   TP 保底缓存，不可再让          │
     0 MB └─────────────────────────────────┘
```

本报告所有"借出深度"均以 **1536 MB** 为分母。

#### 1.3.3 动态池的授信记账

`gs_amm_dynamic_target_mb` 常被误读为"动态池的容量"，实际不是。**它是授信额度账面值的初始值**，且会随借还浮动：

```c
// gs_amm.cpp:6061  借出后，额度随之抬高
if (borrowed_mb > 0)
    shared_state->dynamic_target_mb += borrowed_mb;

// gs_amm.cpp:6074  回收后，额度随之压低
shared_state->dynamic_target_mb = Max(gs_amm_ap_min_grant_mb,
                                      shared_state->dynamic_target_mb - resize_applied_mb);

// gs_amm.cpp:6062  可授信余额 = 额度 − 已授出
free_mb  = Max(shared_state->dynamic_target_mb - shared_state->dynamic_used_mb, 0);
grant_mb = gs_amm_clamp_grant_mb(effective_ap_demand_mb, free_mb);
```

| 字段 | 含义 |
|---|---|
| `dynamic_target_mb` | 当前授信额度上限（账面值，非预留的物理内存） |
| `dynamic_used_mb` | 已授出的额度 |
| `dynamic_free_mb` | `target − used`，还能授出多少 |

初始值由 `gs_amm_dynamic_target_mb` 给定：**编译期默认 512 MB，本测试环境配置为 256 MB**。实测中该值随借还在 256 / 320 / 384 / 448 … 之间移动，每借出一个 granule 抬高 64 MB。

两组测试仅差一个 GUC：

| 组别 | `gs_amm_native_auto_mode` | 含义 |

## 二、测试场景设计

### 2.1 设计原则：场景定义与被测特性无关

这是本次设计的第一原则，直接决定对比是否公平。

**测试场景只用负载侧的量来定义**——TP 并发数、AP 并发数、AP 申请的 `work_mem`、持续时长。这些量在 AMM 开启与关闭两组中含义完全相同，是原生 openGauss 就有的概念。

**不使用任何 `gs_amm_*` 参数来定义场景。** 例如不会写成"让 AP 需求恰好等于动态池初始目标"——因为"动态池"是 AMM 引入的概念，关闭组里不存在，用它定义场景会使两组失去共同基准，对比自然不成立。

压力档位改用**原生物理量**做参照：

| 参照物 | 值 | 来源 |
|---|---|---|
| `max_process_memory` | 4096 MB | 原生 openGauss |
| `shared_buffers` | 2048 MB | 原生 openGauss |

由此，三者严格分开：

| 层次 | 内容 | 是否与特性相关 |
|---|---|---|
| **场景定义** | TP/AP 并发、`work_mem`、时长 | **无关**，两组完全一致 |
| **预期行为** | AMM 开启时应触发什么机制 | 相关，属于**待验证假设** |
| **观测判据** | 采集什么指标、如何判定 | 尽量选两组都可测的量 |

后文每个 step 均按这三层分开陈述。**若把预期行为写进场景定义，就等于先假定特性有效再去验证它。**

### 2.2 五个 step 是一条链，不是五个并列用例

**场景本身只是压力递增**（§2.1 已用负载量定义完毕，与特性无关）。但**开启 AMM 时要观测的那组机制是逐级依赖的**——这决定了结果该怎么读。

按 PPT 的设计，AMM 侧的机制链是：

```
step ①  压力最低
          │
          ▼
step ②  申请量达共享池一半 ──► 应触发：向共享池借内存
          │                     【若这步没借到，后面全部无从谈起】
          ▼
step ③  申请量达共享池全量 ──► 应触发：持续借直到撞上下限，地板保护生效
          │                     【若从未接近地板，地板逻辑不会被执行】
          ▼
step ④  申请量达进程上限   ──► 应触发：无内存可借，新 AP 进入队列
          │                     【若没到地板，就不会进入"无内存可给"的状态】
          ▼
step ⑤  转为 TP 侧加压     ──► 应触发：把借出去的内存收回来保 TP
```

**关闭组不存在这条依赖链**——原生 openGauss 没有借还与队列机制，它在同样的压力递增下自有一套行为（各算子按 `work_mem` 取用、超出则落盘、总量受 `max_process_memory` 兜底）。两组在同一压力序列下各自的表现，才是对比的内容。

因此开启组的结果需要区分两种"没通过"：

- **不成立**：机制被触发了，但行为不符合预期
- **不可判定**：前置条件没达成，机制根本没有机会运行——**这不等于机制有错**，只是本次没测到

关闭组则不适用这套判定，它回答的是另一个问题：同样压力下，不用 AMM 会怎样。


### 2.3 两侧负载各自扮演什么角色

| 负载 | 角色 | 在测试中的作用 |
|---|---|---|
| **TP**（gsbench 101） | **被保护对象** | 提供稳定的基线吞吐。它的吞吐量与抖动是判断"保护是否有效"的直接指标 |
| **AP**（gsbench 201） | **索取方** | 制造大块 `work_mem` 需求并**持续占住**。并发数与单份 `work_mem` 决定压力强度 |

两者的对抗关系是本次要观察的核心：**AP 要内存，TP 要缓存。** 五个 step 就是把这对矛盾从"内存宽裕"逐级推到"内存耗尽"，看系统在每个压力档位上如何取舍。

注意这个描述是中性的——它不预设"谁来调度"。原生 openGauss 的取舍方式是各算子按 `work_mem` 各取所需、由 `max_process_memory` 兜底；AMM 的取舍方式是集中授信与池间迁移。**两种方式在同一组压力档位下的表现，就是本次对比的内容。**

### 2.4 逐步说明

每个 step 持续 **2 分钟**。每步按三层陈述：**场景定义**（与特性无关）、**开启 AMM 时的预期**（待验证假设）、**观测判据**。

---

#### step ① 内存宽裕

**场景定义**

| 项 | 值 |
|---|---|
| TP | 2 worker |
| AP | 2 并发，每份 `work_mem = 128 MB` |
| AP 名义申请合计 | 256 MB |
| 相对 `shared_buffers`(2048 MB) | 12.5% |
| 相对 `max_process_memory`(4096 MB) | 6.3% |

申请量相对两个物理上限都很小，是本次压力序列的**最低档**。

**开启 AMM 时的预期（假设）**

压力轻微，不需要动共享池即可满足 AP。

**观测判据（两组通用）**

- AP 实际获得的算子内存 ≈ 申请值（`Sort Method` 与内存/落盘量）
- TP 吞吐无明显跌落
- 共享池 `active_mb` 无明显移动

这一步不检验借还机制，它提供的是**基线参照**：如果连最低档压力下 AP 都拿不到内存，后续各步的结论都要放在这个前提下解读。

---

#### step ② 申请量抬升至共享池一半　←　**验收①**

**场景定义**

| 项 | 值 |
|---|---|
| TP | 2 worker（不变） |
| AP | 2 并发，每份 `work_mem = 512 MB` |
| AP 名义申请合计 | 1024 MB |
| 相对 `shared_buffers` | **50%** |
| 相对 `max_process_memory` | 25% |

单份 `work_mem` 由 128 MB 提到 512 MB，申请量达到共享缓冲池的一半。

**开启 AMM 时的预期（假设）**

动态侧原有额度不足以覆盖该申请量，应触发 `BORROW_FROM_BUFFER`，把 granule 从共享池迁往动态池。

**观测判据**

| 判据 | 两组均可测 |
|---|---|
| AP 实得算子内存（`Sort Method` / Memory / Disk） | ✅ |
| TP 吞吐与抖动 | ✅ |
| 共享池 `active_mb` 是否下降 | 仅开启组有意义 |
| 动态池 `dynamic_used_mb` 是否上升 | 仅开启组有意义 |

**验收① 的问题**：AP 并发起来，内存有没有借？借出期间 TPS 抖动是否控制在预算内？

这一步需要同时看**两个**开启组指标，缺一不可：

- `active_mb` 下降 → 借的**动作**发生了
- `dynamic_used_mb` 上升 → 借来的内存**到了 AP 手里**

只有前者而无后者，意味着内存被搬出来却没人用。而 AP 实得内存这一项两组都能测，是判断"谁更有效"的公共标尺。

---

#### step ③ 申请量抬升至可借满地板的最小档　←　**验收②**

**场景定义**

| 项 | 值 |
|---|---|
| TP | 2 worker（不变） |
| AP | **7 并发**，每份 `work_mem = 512 MB` |
| AP 名义申请合计 | 3584 MB |
| AP 真实占用（按实测 475 MB/份） | 3325 MB |
| 相对 `shared_buffers`(2048 MB) | 175% |
| 相对 `max_dynamic_memory`(2134 MB) | **168%** |

并发数不是随手取的，是按"刚好能把共享池借到地板"反算出来的最小值，推算见下。

**开启 AMM 时的预期（假设）**

动态空间被占满后，共享池被持续借出并撞上 512 MB 下限，地板保护生效：共享池停止下降，为 TP 保住最低缓存。

**本档并发数的推算依据**

共享池要降到地板，等价于**动态侧必须真实占用足够多的内存**，把需求逼到动态空间之外。按原生口径，用 §1.2.2 实测的内存分解：

```
动态内存上限        max_dynamic_memory   = 2134 MB
空载已用            dynamic_used_memory  =  542 MB
────────────────────────────────────────────────────
AP 可用动态空间                          ≈ 1592 MB   ← 超出此值才需要借
要借满可迁移带宽                          = 1536 MB   （2048 − 512）
────────────────────────────────────────────────────
AP 需消耗总量 = 1592 + 1536              ≈ 3128 MB
```

用实测的单份 AP 真实占用 **475 MB**（原生模式 `EXPLAIN` 实测）折算：

| 并发 | AP 真实占用 | 对 3128 MB 的覆盖 |
|---|---|---|
| 6 AP | 2850 MB | 0.91× |
| **7 AP（本档）** | **3325 MB** | **1.06×** |
| 8 AP | 3800 MB | 1.21× |

**7 并发是刚好越过阈值的最小档位**，故本档取 7。step ④ 的 8 并发提供 1.21× 余量，两档合起来足以支撑地板判定。

> 此处刻意不使用 `gs_amm_dynamic_target_mb` 等 AMM 内部记账量来推算。用被测特性的内部参数去论证"场景需要多大负载"会构成循环，也违反 §2.1 的原则。上述推算全部基于 `max_dynamic_memory`、`shared_buffers`、地板值与实测的 AP 真实占用，两组通用。

> **一个前提**：以上推算成立的前提是"AP 能拿到它申请的内存"。若实测显示 AP 实得远低于申请值，则动态侧占用无法接近 3128 MB，**此时并发数设得再高也不会改变结果**——瓶颈在授信而非压力。结果章节需先确认这一点。

因此本档的定位应为：

| 能验证 | 不能验证 |
|---|---|
| 共享池是否会从 2048 MB 往下缩 | 是否**能到达**地板 |
| 缩小过程中 TP 是否仍可维持 | 地板逻辑本身是否正确 |

**地板的稳健验证依赖 step ④（8 并发，2.29× 余量）。** 若两档均未接近地板，则应判为"不可判定"而非"不成立"——因为压力可能根本没推到位。

**观测判据**

- 共享池 `active_mb` 是否随压力下降（开启组）
- 下降幅度与 1536 MB 可迁移带宽的比值（开启组）
- TP 吞吐在高压下是否仍能维持（两组）
- AP 实得内存（两组）

**验收② 的问题**：借了 TP 的内存之后，有没有托底保护？到了地板是否停止让渡？

托底是 TP 的最后一道防线——没有下限，索取方可以把缓存抽干。原生 openGauss 侧的对应保护是各算子 `work_mem` 上限与超限落盘（`max_process_memory` 在本环境未强制，见 §1.2），两种保护方式的实际效果在此对比。

---

#### step ④ 申请量抬升至进程上限（刻意超额）　←　**验收③**

**场景定义**

| 项 | 值 |
|---|---|
| TP | 2 worker（不变） |
| AP | **8 并发**，每份 `work_mem = 512 MB` |
| AP 名义申请合计 | 4096 MB |
| 相对 `shared_buffers` | 200% |
| 相对 `max_process_memory` | **100%** |

**这是刻意的超额申请。** 名义申请合计恰好等于整个 `max_process_memory`，而 `shared_buffers` 自己就占掉其中 2048 MB（§1.2），因此**该申请量在物理上不可能被完全满足**——这正是设计意图。只有把系统推进"确实无内存可给"的状态，才能观察它如何处理无法满足的请求。

**开启 AMM 时的预期（假设）**

无内存可再借时，新到的 AP 应进入等待队列，而不是被静默降级或直接失败。

**观测判据**

本步**不考核"AP 是否都拿到内存"**（物理上做不到），只考核**拿不到的那些如何被处理**：

| 结局 | 对业务的含义 |
|---|---|
| 进入队列等待 | 稍后可得，查询性能可预期 |
| 直接反压、回退到较小 `work_mem` | 静默降级，查询变慢但不报错 |
| 报错失败 | 业务可见的失败 |

三者对业务影响完全不同。开启组看队列相关计数器；关闭组看原生 openGauss 在同样超额下的表现（是否报错、是否落盘）。

**验收③ 的问题**：AP 持续增加时，是否开启队列保护？新排序是否进入队列？

---

#### step ⑤ 转为 TP 侧加压　←　**验收④**

**场景定义**

| 项 | 值 |
|---|---|
| TP | **由 2 worker 阶跃到 8 worker** |
| AP | 8 并发，每份 512 MB（**不变**） |
| 变化方向 | 前四步是 AP 侧加压，本步转为 TP 侧加压 |

AP 压力保持不变，TP 流量放大 4 倍，缓存竞争加剧、`buffer_hit` 下降。

**开启 AMM 时的预期（假设）**

TP 压力上升应被感知，先前借给 AP 的内存应被收回共享池，优先保障 TP。

**观测判据**

- `buffer_hit` 是否随 TP 加压而下降（两组）
- 共享池 `active_mb` 是否回升（开启组）
- TP 吞吐是否得到改善（两组）

**验收④ 的问题**：TP 流量增加、`buffer_hit` 下降时，会不会回补 TP 共享缓存？

前四步看"能不能把内存给出去"，这一步看"能不能在 TP 需要时要回来"。**单向的让渡不是调度，双向可逆才是。**

### 2.5 压力序列总览

| step | 场景 | TP worker | AP 并发 | AP work_mem | 名义申请 | 真实占用<br>(475 MB/份) | 占 `shared_buffers`<br>2048 MB | 占 `max_dynamic_memory`<br>2134 MB | 对应验收 |
|---|---|---|---|---|---|---|---|---|---|
| ① | 内存宽裕 | 2 | 2 | 128 MB | 256 MB | — | 12.5% | 12.0% | 基线 |
| ② | 抬至共享池一半 | 2 | 2 | 512 MB | 1024 MB | 950 MB | 50% | 44.5% | **① 有没有借** |
| ③ | 可借满地板的最小档 | 2 | **7** | 512 MB | 3584 MB | 3325 MB | 175% | **156%** | **② 托底保护** |
| ④ | 超额申请 | 2 | 8 | 512 MB | 4096 MB | 3800 MB | 200% | **178%** | **③ 队列保护** |
| ⑤ | 转 TP 侧加压 | **8** | 8 | 512 MB | 4096 MB | 3800 MB | 200% | 178% | **④ 回补缓存** |

压力沿两个方向递增：**① → ④ 是 AP 侧加压**（256 → 4096 MB），**⑤ 转为 TP 侧加压**（2 → 8 worker）。前者测"给得出去"，后者测"收得回来"。

全部档位均以原生 openGauss 的量为参照——`shared_buffers`、`max_dynamic_memory`、地板值与实测 AP 真实占用，**不含任何 AMM 参数**，因此两组适用同一套场景。

### 2.6 档位是如何反算出来的

step ③ 的 7 并发不是经验取值，而是按"刚好能把共享池借到地板"反算的最小档位。完整推导：

```
① 动态空间还剩多少可用
   max_dynamic_memory   2134 MB      （§1.2.2 实测）
 − dynamic_used_memory   542 MB      （空载）
 ────────────────────────────────
   AP 可用动态空间     ≈ 1592 MB      ← 用满这些之前，不需要向共享池借

② 借满可迁移带宽还需多少
   可迁移带宽           1536 MB      （2048 − 512）

③ 合计：AP 需真实占用  ≈ 3128 MB
```

按实测单份真实占用 475 MB 折算：

| 并发 | 真实占用 | 对 3128 MB | 判定 |
|---|---|---|---|
| 6 | 2850 MB | 0.91× | 不足 |
| **7** | **3325 MB** | **1.06×** | **最小可行档** |
| 8 | 3800 MB | 1.21× | 有余量 |

**故 step ③ 取 7，step ④ 取 8。** 两档均越过阈值，step ④ 另有 1.21× 余量，可作为地板判定的佐证档。

> **一个前置判断**：以上推算成立的前提是"AP 能拿到它申请的内存"。若实测显示 AP 实得远低于申请值（例如只有个位数 MB），则动态侧真实占用无法接近 3128 MB，**此时并发数设得再高也不会改变结果**——瓶颈在授信而非压力。结果章节需先确认这一点，再判断地板不可达的归因。

### 2.7 对照组的设计意图

同一套五阶段编排，在 AMM 开启与关闭两种模式下各跑一遍。

开启组回答"AMM 的行为是否符合其设计"，关闭组回答另外两个问题：

1. **这套负载本身是否有效？** 若关闭 AMM 后 AP 能正常拿到内存、TP 正常受压，说明负载构造是对的，开启组的异常不能归咎于测试方法。
2. **AMM 带来的净效果是正是负？** 两组在同一压力档位下的 AP 表现与 TP 表现之差，就是 AMM 介入的实际收益或代价。

这是本次相较以往测试的关键改进：**以往只测 AMM 开启时的绝对表现，无法回答"不用 AMM 会怎样"。** 有了对照组，每条结论都有了参照基准，也才谈得上公平。

本次两组还共享一个此前不具备的前提：**内存保护已启用**（§1.2.2）。这意味着关闭组的 AP 会真实受到 2134 MB 动态内存上限的约束，其表现代表"原生 openGauss 在内存确实不足时会怎么做"，而不再是"内存无限供应时的表现"。这使对比更接近生产语义。
