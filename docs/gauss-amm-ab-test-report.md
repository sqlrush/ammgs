### 1.2 内存池布局

这是理解全部测试结果的基础。要点是**存在两层上限**：外层是 openGauss 的进程总上限，内层才是 AMM 可以腾挪的范围。

#### 外层：`max_process_memory` —— 借和还都跑不出这个信封

| 参数 | 值 | 级别 |
|---|---|---|
| `max_process_memory` | **4096 MB（4 GB）** | postmaster，改需重启 |
| `shared_buffers` | 2048 MB | postmaster |
| `cstore_buffers` | 512 MB | postmaster |
| `wal_buffers` | 16 MB | postmaster |
| `max_connections` | 200 | postmaster |

`max_process_memory` 限定的是**数据库进程能用的内存总量**，共享内存与动态内存都在其中：

```
max_process_memory = 4096 MB  ← 硬上限，AMM 无权突破
│
├─ 共享内存部分
│   ├─ shared_buffers   2048 MB   ← AMM 的 max_mb，借出的来源
│   ├─ cstore_buffers    512 MB
│   ├─ wal_buffers        16 MB
│   └─ 其他共享结构
│
└─ 动态内存部分（会话上下文、work_mem 等）
    └─ AMM 动态池 / AP 的排序内存从这里出
```

**AMM 做的是在这个固定信封内部重新分配，而不是增加内存总量。** 一个 granule 从 `shared_buffers` 迁到动态池，是共享内存减少 64 MB、动态内存增加 64 MB，两侧之和不变。因此：

- **借**：`shared_buffers` 缩小，动态池扩大，总量不变
- **还**：反向，总量仍不变
- **任何时刻，共享池 + 动态池 ≤ `max_process_memory`**

这条约束是硬的。后文所有"借出深度""让渡"都应在这个前提下理解——AMM 不能也不会突破 4 GB。

#### 内层：AMM 的可迁移带宽

| 项 | 值 | 说明 |
|---|---|---|
| `shared_buffers` | 2048 MB | 即 AMM 的 `max_mb`，共享池上限 |
| `gs_amm_granule_size_mb` | 64 MB | 迁移的最小单位 |
| 折合 granule 数 | **32 个** | 2048 / 64 |
| `gs_amm_shared_buffers_min_mb` | 512 MB | **地板**，共享池不得低于此值（8 granule） |
| `gs_amm_dynamic_target_mb` | 256 MB | 动态池的初始目标 |
| **可迁移带宽** | **1536 MB = 24 granule** | 2048 − 512，共享池最多能让出这么多 |

```
  2048 MB ┌─────────────────────────────────┐  ← max_mb，共享池上限
          │                                 │
          │   可迁移带宽 1536 MB（24 个 granule）│  ← 借出只能在这个区间内发生
          │                                 │
   512 MB ├─────────────────────────────────┤  ← 地板 shared_buffers_min_mb
          │   TP 保底缓存，不可再让          │
     0 MB └─────────────────────────────────┘
```

本报告所有"借出深度"均以 **1536 MB** 为分母。

#### 由此得到的一个硬约束

`shared_buffers` 单独就占掉 `max_process_memory` 的一半（2048 / 4096）。即使 AMM 把可迁移带宽全部让给 AP，动态侧能拿到的内存也有明确天花板：

```
动态侧理论最大 ≈ (max_process_memory − 共享内存固定部分) + 已借出的 granule
              ≈ (4096 − 2048 − 512 − 其他) + 1536
```

**这意味着 AP 的名义需求可以超过物理可满足量。** 本次测试的 step ④ 正是刻意设计成这样（见 §2.3），用来触发队列机制——不是配置失误。

| 组别 | `gs_amm_native_auto_mode` | 含义 |

## 二、测试场景设计

### 2.1 五个 step 是一条链，不是五个并列用例

这一点决定了结果该怎么读。PPT 的五个阶段是**逐级递进**的：每一步要观测的机制，都以上一步成功为前提。

```
step ①  内存富裕
          │  AP 需求还在动态池内，不需要借
          ▼
step ②  触及上限 ──► 需求超出动态池，必须向共享池借
          │           【若这步没借到，后面全部无从谈起】
          ▼
step ③  保护基准 ──► 持续借，直到撞上 512 MB 地板
          │           【若从未接近地板，地板逻辑不会被执行】
          ▼
step ④  反压排队 ──► 地板之下无内存可借，新 AP 只能排队
          │           【若没到地板，就不会进入"无内存可借"的状态】
          ▼
step ⑤  基准突增 ──► TP 流量暴涨，把借出去的内存收回来保 TP
```

因此结果需要区分两种"没通过"：

- **不成立**：机制被触发了，但行为不符合预期
- **不可判定**：前置条件没达成，机制根本没有机会运行——这不等于机制有错，只是本次没测到

### 2.2 两侧负载各自扮演什么角色

| 负载 | 角色 | 在测试中的作用 |
|---|---|---|
| **TP**（gsbench 101） | **被保护对象** | 提供稳定的基线吞吐。AMM 的 `tp_baseline_tps` / `tp_recent_tps` / `drop_ratio` 全部依赖它。它的吞吐和抖动是判断"保护是否有效"的直接指标 |
| **AP**（gsbench 201） | **索取方** | 制造大块 `work_mem` 需求并**持续占住**。它的并发数和单份内存决定了对共享池的压力强度 |

两者的对抗关系是整个方案的核心：**AP 要内存，TP 要缓存，AMM 负责在两者之间调度。** 五个 step 就是把这个对抗从"内存富裕"逐级推到"内存耗尽"，看 AMM 在每个压力档位上的动作。

### 2.3 逐步说明

每个 step 持续 **2 分钟**。

---

#### step ① 内存富裕

| | |
|---|---|
| **动作** | TP 2 worker 稳定运行；AP 2 并发，每份申请 `work_mem=128MB` |
| **AP 总需求** | 256 MB |
| **场景含义** | 动态池初始目标就是 256 MB，需求恰好落在动态池容量内 |
| **应触发的机制** | 无需借用共享池，AMM 用自有动态池即可满足 |
| **测试目标** | **建立基线**——确认内存宽裕时 AP 能正常拿到内存、TP 不受干扰 |
| **判据** | AP 实得 ≈ 申请值；共享池 `active_mb` 不下降；TP 吞吐无明显跌落 |

这一步不检验借还机制，它的价值是提供后续对比的参照点：如果连内存富裕时 AP 都拿不到内存，那么后面的"借"就失去了意义。

---

#### step ② 触及上限　←　**验收①：内存有没有借出来**

| | |
|---|---|
| **动作** | TP 不变；AP 2 并发，每份申请 `work_mem=512MB` |
| **AP 总需求** | 1024 MB |
| **场景含义** | 需求 1024 MB 远超动态池的 256 MB，缺口必须从共享池借 |
| **应触发的机制** | `BORROW_FROM_BUFFER`——granule 从 `shared_buffers` 迁往动态池 |
| **测试目标** | **① AP 并发起来，内存有没有借？借出期间 TPS 抖动是否控制在预算内？** |
| **判据** | `active_mb` 下降（共享池让出）；`dynamic_used_mb` 上升并接近需求（AP 真的用上了）；TPS 抖动在阈值内 |

这是整条链的**关键一步**。需要同时看两个量：

- `active_mb` 下降 → 说明**借的动作发生了**
- `dynamic_used_mb` 上升 → 说明**借来的内存到了 AP 手里**

两者缺一不可。只有前者而无后者，意味着内存被搬出来却没人用；两者都无，则借出根本没发生。

---

#### step ③ 保护基准　←　**验收②：托底保护**

| | |
|---|---|
| **动作** | TP 不变；AP 提升到 4 并发，每份仍 512 MB |
| **AP 总需求** | 2048 MB |
| **场景含义** | 需求继续加码，共享池被持续借出，逼近 512 MB 地板 |
| **应触发的机制** | 地板保护——`active_mb` 降到 `shared_buffers_min_mb` 后停止下降，为 TP 保住最低缓存 |
| **测试目标** | **② 借了 TP 的内存之后，有没有托底保护？到了地板是否停止让渡、动态池不再扩张？** |
| **判据** | `active_mb` 触及 512 MB 后不再下降；`dynamic_target_mb` 停止增长；TP 在保底缓存下仍能维持吞吐 |

这一步检验的是"让渡有没有下限"。**托底保护是 TP 的最后一道防线**——没有它，AP 可以把共享池抽干，TP 会因缓存崩塌而不可用。

---

#### step ④ 反压排队　←　**验收③：队列保护**

| | |
|---|---|
| **动作** | TP 不变；AP 提升到 8 并发，每份仍 512 MB |
| **AP 总需求** | 4096 MB |
| **场景含义** | 共享池已在地板，无内存可再借，而新的 AP 仍在到来 |
| **应触发的机制** | 反压与排队——新的慢 SQL 进入等待队列，而不是被静默降级或直接拒绝 |
| **测试目标** | **③ 托底保护之后 AP 持续增加，是否开启队列保护？新排序是否进入队列？** |
| **判据** | `ap_queue_len` > 0；`ap_queue_admit_count` 随压力增长；入队占反压的比例合理 |

排队的意义在于**给内存一个"稍后可得"的机会**，而不是让查询立刻退化。这一步要区分三种结局：进队列等待、直接反压回退到 `fallback_work_mem_kb`、或报错失败——三者对业务的影响完全不同。

> **这一步是刻意的超额申请。** AP 名义总需求 4096 MB，恰好等于整个 `max_process_memory`，而 `shared_buffers` 自己就占掉其中 2048 MB（§1.2）。**这个需求在物理上不可能被完全满足，这正是设计意图**——只有把系统推进"确实没有内存可给"的状态，队列机制才会被触发。因此本步不考核"AP 是否都拿到内存"，只考核**拿不到的那些是进了队列，还是被静默降级**。

---

#### step ⑤ 基准突增　←　**验收④：回补共享缓存**

| | |
|---|---|
| **动作** | TP 从 2 worker **阶跃到 8 worker**；AP 保持 8 并发 |
| **AP 总需求** | 4096 MB（不变） |
| **场景含义** | TP 流量突然放大 4 倍，缓存需求随之上升，`buffer_hit` 下降 |
| **应触发的机制** | `TP_RECOVERY`——把先前借给 AP 的 granule 收回共享池，优先保障 TP |
| **测试目标** | **④ TP 内存被托底后，TP 流量增加、buffer_hit 下降时，会不会回补 TP 共享缓存？** |
| **判据** | `buffer_hit` 下降被 AMM 感知；`active_mb` 回升；TP 吞吐得到恢复 |

这一步检验调度的**双向性**：前四步都在看"能不能把内存借给 AP"，这一步看"能不能在 TP 需要时要回来"。单向的让渡不是调度，只有双向可逆才算。

### 2.4 五个 step 与四项验收的对应

| step | 阶段名 | TP worker | AP 并发 | AP work_mem | AP 总需求 | 对应验收 |
|---|---|---|---|---|---|---|
| ① | 内存富裕 | 2 | 2 | 128 MB | 256 MB | 基线，无验收 |
| ② | 触及上限 | 2 | 2 | 512 MB | 1024 MB | **① 内存有没有借** |
| ③ | 保护基准 | 2 | 4 | 512 MB | 2048 MB | **② 托底保护** |
| ④ | 反压排队 | 2 | 8 | 512 MB | 4096 MB | **③ 队列保护** |
| ⑤ | 基准突增 | **8** | 8 | 512 MB | 4096 MB | **④ 回补共享缓存** |

压力沿两个方向递增：**step ①→④ 是 AP 侧加压**（256 → 4096 MB），**step ⑤ 转为 TP 侧加压**（2 → 8 worker）。前者测"给得出去"，后者测"收得回来"。

### 2.5 对照组的设计意图

同一套五阶段编排，在 AMM 开启和关闭两种模式下各跑一遍。

开启组回答的是"AMM 的行为是否符合设计"，关闭组回答的是另外两个问题：

1. **这套负载本身是否有效？** 如果关闭 AMM 后 AP 能正常拿到内存、TP 正常受压，说明负载构造是对的，开启组的异常不能归咎于测试方法。
2. **AMM 带来的净效果是正是负？** 把两组的 AP 表现和 TP 表现直接相减，得到的就是 AMM 介入的实际收益或代价。

这是本次测试相较以往的关键改进：**以前只测 AMM 开启时的绝对表现，无法回答"不用 AMM 会怎样"。** 有了对照组，每一条结论都有了参照基准。
